================================================================================
                    GESTION MAGASINS — RÉSUMÉ DU PROJET
                    (état au 5 septembre 2026)
================================================================================

SaaS multi-tenant de gestion de magasins (point de vente, stock, produits,
clients, fournisseurs, rapports) avec fonctionnement HORS LIGNE (PWA).

--------------------------------------------------------------------------------
2. ARCHITECTURE MULTI-TENANT
--------------------------------------------------------------------------------

  - Une COMPANY (entreprise) = un tenant. Elle possède plusieurs STORES
    (magasins).
  - Un USER peut appartenir à plusieurs entreprises via des MEMBERSHIPS
    (un membership = user + company + role + store optionnel).
  - Le tenant courant est résolu par TenantMiddleware à partir du claim
    `company_id` du JWT (jamais depuis le body ou un header).
  - Endpoint /api/auth/switch-company/ pour changer d'entreprise (nouveau
    JWT).
  - Isolation à deux niveaux :
      * scope COMPANY : accès à tous les magasins de l'entreprise
      * scope STORE   : accès restreint au magasin assigné au membership
    (request.scope et request.store injectés par HasPermission)

MÉCANISME DE VÉRIFICATION (backend/users/permissions.py)
  Classe HasPermission : 1) user actif  2) entreprise active
                         3) membership actif  4) permission du rôle
  Configuration sur les vues : `required_permission` (code unique) ou
  `permission_map` ({action DRF ou méthode HTTP : code}).
  Autres classes : IsCompanyMember, IsSuperAdmin, IsSupportAdmin.

  Côté frontend : useAuth().hasPermission(code) ; les applications et
  sous-sections du dashboard sont filtrées via frontend/src/config/appsCatalog.js.

5. TABLES DE LA BASE DE DONNÉES (PostgreSQL)
--------------------------------------------------------------------------------

Conventions :
  - id        BigAutoField, clé primaire interne (jamais exposée dans l'API)
  - uuid      UUID unique, identifiant public utilisé par l'API et le frontend
  - FK        clé étrangère ; comportement à la suppression indiqué
              (CASCADE = supprimé avec le parent, SET_NULL = mis à NULL,
               PROTECT = suppression interdite)
  - Soft delete = colonnes is_deleted (bool, défaut false) + deleted_at
  - Les montants sont des Decimal(12,2) en FCFA

--- APP inventory -----------------------------------------------------------

TABLE inventory_movements  (historique des mouvements de stock)
  id                  BigAuto        PK
  uuid                UUID           unique
  company_id          FK companies   CASCADE
  store_id            FK stores      CASCADE

                                     mouvements existants)

5 bis. TABLES LOCALES INDEXEDDB (frontend, Dexie — frontend/src/pwa/db.js)
--------------------------------------------------------------------------------

Base : une seule base IndexedDB versionnée (DB_VERSION). Chaque ligne porte
company_uuid, store_uuid, user_uuid, device_uuid pour isoler les données par
entreprise / magasin / utilisateur / appareil.

Format Dexie : "cléPrimaire, index1, index2, ..." ; "++id" = auto-incrément.

CACHE DE LECTURE (copie des données serveur, rafraîchie au login et à chaque
synchronisation)
  products        uuid, company_uuid, store_uuid, user_uuid, device_uuid,
                  name, updated_at
                  (+ champs métier : stock_quantity, stock_by_store, prix...)
  categories      uuid, company_uuid, store_uuid, user_uuid, device_uuid,
                  name, updated_at
  customers       uuid, company_uuid, user_uuid, device_uuid, name, updated_at
  suppliers       uuid, company_uuid, user_uuid, device_uuid, name, updated_at
  stores          uuid, company_uuid, user_uuid, device_uuid, name, updated_at
  settings        key, company_uuid, user_uuid, device_uuid, updated_at

FILE D'ATTENTE ET JOURNAL
  syncQueue       ++id, operation_uuid, company_uuid, store_uuid, user_uuid,
                  device_uuid, entity_type, entity_uuid, operation_type,
                  status, created_at, synced_at
                  - entity_type    : product | category | customer | supplier
                                     | sale | posSession | stockMovement
                                     | stockTransfer | inventory
                  - operation_type : CREATE | UPDATE | DELETE
                  - status         : PENDING_SYNC | SYNCING | SYNCED | FAILED
                                     | conflict
                  - payload        : corps de la requête à rejouer
                  - retry_count, last_error
  syncLog         ++id, company_uuid, store_uuid, user_uuid, device_uuid,
                  entity_type, operation_type, status, message, created_at

DONNÉES CRÉÉES HORS LIGNE
  posSessions     uuid, company_uuid, store_uuid, user_uuid, device_uuid,
                  status, created_at
  sales           uuid, company_uuid, store_uuid, user_uuid, device_uuid,
                  status, created_at
                  (+ items[], total_amount, payment_method, is_deleted)
  stockMovements  uuid, company_uuid, store_uuid, user_uuid, device_uuid,
                  product_uuid, movement_type, status, created_at
                  (+ quantity, note, from_store, to_store, is_deleted)
  preferences     key, company_uuid, user_uuid, device_uuid

CORRESPONDANCE entity_type -> table locale (ENTITY_TO_TABLE)
  product -> products          category -> categories
  customer -> customers        supplier -> suppliers
  sale -> sales                posSession -> posSessions
  stockMovement / stockTransfer / inventory -> stockMovements

NETTOYAGE
  clearCompanyData(companyUuid) : vide les caches d'une entreprise
  clearCacheData()              : vide les caches au logout mais PRÉSERVE
                                  syncQueue et posSessions (aucune perte
                                  d'opération non synchronisée)

POINT DE VENTE (/pos)
  - Sélection du magasin (scope COMPANY) ou magasin assigné (scope STORE)
  - Recherche produits, panier, quantités contrôlées par le stock disponible
  - Paiement : espèces, Mobile Money (Chap Chap Pay), carte, crédit
  - Fonctionne hors ligne (vente mise en file d'attente)

CONTRÔLES DE STOCK (frontend)
  - Entrée : quantité > 0
  - Ajustement : quantité >= 0
  - Transfert : quantité > 0 et <= stock du magasin source
  - Vente : quantité <= stock disponible (y compris offline)

                  operation_type CREATE|UPDATE|DELETE, status, payload)
  syncLog        journal de synchronisation
  posSessions    sessions de caisse locales
  sales          ventes créées hors ligne / cache
  stockMovements mouvements de stock hors ligne / cache
  preferences    préférences locales
  Toutes les lignes portent company_uuid / store_uuid / user_uuid / device_uuid.

9. SÉCURITÉ ET RÈGLES MÉTIER
--------------------------------------------------------------------------------

  - JWT obligatoire ; company_id issu du token uniquement.
  - Toutes les requêtes filtrées par request.company (et request.store si
    rôle STORE).
  - Rôles système non supprimables.
  - Stock jamais négatif (StockLevel.quantity PositiveIntegerField, contrôles
    frontend + backend).
  - Soft delete sur produits, catégories, clients, fournisseurs.
  - Journal d'audit (audit_logs) sur les actions sensibles : création /
    annulation de vente, annulation de mouvement de stock, etc.
  - Fichiers uploadés scannés par ClamAV, stockés dans MinIO, isolés par
    entreprise / magasin.
  - Entreprise suspendue ou annulée => accès bloqué (Company.is_active).
