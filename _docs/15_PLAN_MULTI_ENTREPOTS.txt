ETAPE 3 — TRANSFERTS TYPES AVEC STATUTS (R16-R48, R76-R83)
============================================================

3.1  Nouvelle table transfers
       id, uuid, company FK, number Char(30) unique (TR-2026-000001),
       transfer_type : intra_warehouse | inter_warehouse | inter_store
       from_store, to_store, from_warehouse, to_warehouse,
       from_location (nullable), to_location (nullable)
       status : draft | requested | validated | prepared | shipped |
                in_transit | received | cancelled | rejected      (R38)
       requested_by, validated_by, shipped_by, received_by (FK users)
       requested_at, validated_at, shipped_at, received_at
       note, reason, created_at, updated_at

     Nouvelle table transfer_items
       id, transfer FK CASCADE, product FK PROTECT, variant FK nullable,
       lot FK nullable, quantity_requested, quantity_shipped,
       quantity_received
       (un transfert peut porter plusieurs produits ; le doc parle
       d'un produit mais rien n'interdit plusieurs lignes)

3.2  Type déduit automatiquement (R37, R41-R44) :
       from_warehouse == to_warehouse             -> intra_warehouse
         (from_location != to_location obligatoire)
       from_store == to_store, warehouses !=      -> inter_warehouse
       from_store != to_store                     -> inter_store
     Le client ne peut pas forcer un type incohérent.

3.3  Machine à états (inventory/transfer_workflow.py)
       draft -> requested -> validated -> prepared -> shipped
             -> in_transit -> received
       Tout état non terminal -> cancelled (par le demandeur/valideur)
       requested -> rejected (par le valideur)
     Effets sur le stock :
       shipped   : apply_movement(transfer_out) sur la source ;
                   quantity_shipped figée ; statut passe à in_transit
       received  : apply_movement(transfer_in) sur la destination
                   avec quantity_received ; écart éventuel
                   (shipped - received) -> mouvement loss sur la
                   destination avec reason="transfer_discrepancy"
                   (R36 : conservation hors pertes)
       cancelled après shipped : mouvement transfer_in de retour
                   sur la source (le stock ne disparaît jamais, R24)

3.4  Transit (R39-R40) : aucune ligne stock_levels fictive. La quantité
     en transit = somme des transfer_items où
     transfer.status = in_transit. Exposée par
     GET /api/inventory/stock/ sous la clé in_transit et dans le
     total tenant (R45) : total = stocks + transit.

3.5  Mode simple (doc 07, public peu à l'aise avec l'écrit) :
       POST /api/inventory/transfers/ avec immediate=true enchaîne
       requested -> validated -> shipped -> received dans UNE
       transaction atomique. C'est le comportement de l'écran actuel ;
       l'ancienne action POST /api/inventory/transfer/ est conservée
       comme alias qui appelle ce chemin.

3.6  Invariants testés (R26-R27, R82-R83)
       - stock total store inchangé après transfert inter-entrepôts
       - stock total entrepôt inchangé après transfert intra-entrepôt
       - stock total tenant (stocks + transit) inchangé à chaque étape
       - aucun mouvement de type sale_* / purchase_* créé (R76-R79)
       - aucune écriture dans sales (pas de CA, pas de marge, R77-R78)

3.7  API
       CRUD /api/inventory/transfers/
       POST /api/inventory/transfers/{uuid}/validate|prepare|ship|
            receive|cancel|reject
       GET  /api/inventory/transfers/?status=&type=&store=&warehouse=

3.8  Permissions
       inventory.stock_transfer          créer / brouillon / demander
       inventory.transfer_validate       valider / rejeter
       inventory.transfer_ship           préparer / expédier
       inventory.transfer_receive        recevoir
       inventory.transfer_cancel         annuler
       Manager : tout ; Stock Manager : tout sauf validate ;
       Cashier : aucun.
     Un rôle STORE ne peut agir que sur les transferts dont son
     magasin est source (ship / cancel) ou destination (receive).

3.9  Frontend
       TransferForm : choix produit(s), source (store/entrepôt/
       emplacement), destination ; type affiché automatiquement ;
       bouton "Transférer maintenant" (immediate) et "Créer une
       demande" (workflow).
       TransferList : filtres par statut, badges couleur, actions
       selon permission et étape.
       StockAvailabilityView : colonne "En transit".

3.10 Offline : seul immediate=true est autorisé hors ligne ; les
     actions de workflow exigent le réseau (marquées online-only
     dans offlineModules.js) pour éviter deux appareils qui font
     avancer le même transfert. applyPendingStock traite un transfert
     immédiat en attente comme out sur la source + in sur la
     destination.

ETAPE 9 — MODULE ACHATS ET VALORISATION DU STOCK
============================================================

9.1  Tables
       purchase_orders
         id, uuid, company FK, store FK, warehouse FK (réception
         prévue), supplier FK PROTECT, number (PO-2026-000001) unique,
         status : draft | sent | partially_received | received |
                  cancelled
         expected_at, ordered_by, ordered_at, total_amount, note
       purchase_order_items
         id, order FK CASCADE, product FK PROTECT, variant nullable,
         quantity_ordered, quantity_received, unit_cost, discount
       purchase_receipts  (bon de réception)
         id, uuid, company FK, order FK nullable (réception directe
         sans commande autorisée), warehouse FK, location nullable,
         supplier FK, number (GR-2026-000001), received_by,
         received_at, note
       purchase_receipt_items
         id, receipt FK, product, variant, lot FK nullable (créé à
         la volée si numéro de lot saisi), quantity, unit_cost,
         expiry_date nullable
       supplier_invoices
         id, uuid, company FK, supplier FK, receipt FK nullable,
         number, amount, due_date, status : unpaid | partial | paid
       supplier_payments
         id, uuid, invoice FK, amount, method, paid_at, paid_by

9.2  Réception = apply_movement(type=purchase_in,
     source=purchase_receipt) par ligne, sur l'entrepôt/emplacement
     de réception. Le type "in" manuel actuel (StockEntryForm)
     devient une réception directe sans commande (receipt sans
     order), ce qui garantit qu'une entrée de stock a toujours un
     coût et un fournisseur (ou "Inconnu").

9.3  Valorisation : nouvelle table stock_valuations
       id, product FK, variant nullable, store FK, warehouse FK,
       method : average | fifo,  average_cost Decimal(12,4),
       quantity, total_value, updated_at
     - Méthode par défaut : coût moyen pondéré (PMP), recalculé à
       chaque purchase_in : (Q0*C0 + Qn*Cn) / (Q0+Qn).
     - FIFO optionnel via table fifo_layers (quantité restante par
       réception) pour les activités à lots/péremption.
     - Product.purchase_price devient un "dernier coût connu"
       informatif ; la marge réelle utilise average_cost.
     - sale_items : ajouter unit_cost (figé à la vente) -> marge par
       ligne = (unit_price - discount - unit_cost) * quantity.

9.4  Rapprochement : rapport commandé / reçu / facturé par
     fournisseur ; écarts de réception -> statut partially_received
     et relance.

9.5  Permissions (nouveau module "purchases" dans le catalogue 08)
       purchases.view / create / update / delete / receive / approve
       purchases.view_cost (voir les coûts et marges : Owner, Company
       Admin, Manager, Accountant ; PAS Cashier)
     Templates : Stock Manager -> view/create/receive ;
     Accountant -> view + supplier_invoices/payments.

9.6  API
       CRUD /api/purchases/orders/  + actions send / cancel
       POST /api/purchases/orders/{uuid}/receive/  (partiel autorisé)
       CRUD /api/purchases/receipts/
       CRUD /api/purchases/invoices/  + POST {uuid}/pay/
       GET  /api/reports/valuation/?store=&warehouse=

9.7  Frontend : application "Achats" (Commandes, Réceptions,
     Factures fournisseurs). Réception mobile-first : scan du
     code-barres, saisie de la quantité, lot/péremption si activés.
     StockEntryForm redirige vers "Réception directe".

9.8  Offline : réception directe autorisée hors ligne (mouvement +
     coût) ; commandes/factures online-only. La valorisation est
     recalculée côté serveur à la synchronisation (idempotent par
     receipt uuid, RÈGLE 9 doc 04).

     Une vente peut être réglée 50% cash + 50% Mobile Money.
     Sale.payment_method devient dérivé (mixed si > 1 ligne).

11.3 Crédit client : Customer + credit_limit, current_balance.
       Table customer_payments : id, customer FK, sale FK nullable,
       amount, method, paid_at. Vente à crédit -> balance +, paiement
       -> balance -. Alerte si balance > credit_limit.
       Rapport "Créances clients" avec ancienneté (0-30, 30-60, >60 j).

11.4 Remises et promotions structurées
       Table discounts : id, company FK, store FK nullable, name,
       type : percent | fixed, value, scope : sale | item | category,
       min_quantity nullable, starts_at, ends_at, is_active
       sale_items.discount reste le montant appliqué ; ajout
       discount FK nullable pour la traçabilité (pos.apply_discount
       déjà au catalogue).

11.5 Retours, avoirs et remboursements
       Table sale_returns : id, uuid, sale FK, number (RT-…),
       reason, refund_method, total, created_by, created_at
       Table sale_return_items : return FK, sale_item FK, quantity,
       restock Bool (retour en stock -> apply_movement(return_in)
       ou casse -> loss)
       Table credit_notes (avoirs) : customer FK, amount, balance,
       expires_at ; utilisable comme moyen de paiement.
       L'écran RefundsList actuel bascule sur ce modèle.

11.6 Taxes : table taxes (name, rate, is_inclusive), Product.tax FK
     nullable, CompanySettings.default_tax. sale_items : tax_rate,
     tax_amount figés. Rapport TVA collectée / déductible (achats).

11.7 Numérotation légale : séquences par company et par type
     (ventes, retours, avoirs, PO, GR) sans trou, table
     document_sequences(company, type, year, last_number) avec
     select_for_update. Receipt.receipt_number utilise cette
     séquence.

11.8 Permissions : pos.manage_cash, sales.view_margin,
     customers.manage_credit, sales.return.

11.9 Offline : ventes multi-paiements, retours et cash_movements
     autorisés hors ligne ; clôture de caisse autorisée hors ligne
     mais le rapport Z n'est généré qu'à la synchronisation.

DECISIONS PRISES POUR RESPECTER LE DOC 14
============================================================

D1  Product.store devient obligatoire ; les produits partagés sont
    dupliqués par store (R50-R51). Conséquence : un même article vendu
    dans deux magasins = deux fiches produit, chacune avec ses prix
    (cohérent avec "prix propres au store", R93).

D2  Le transit n'est pas un entrepôt ni un emplacement : c'est une
    quantité portée par le Transfer (évite des stock_levels fictifs
    et respecte R40 littéralement).

D3  L'ancien endpoint POST /api/inventory/transfer/ et l'écran actuel
    restent fonctionnels via immediate=true (aucune régression pour
    les utilisateurs actuels).

D4  Les entrepôts sans emplacements sont autorisés (stock sur
    location=NULL) ; le passage aux emplacements se fait par entrepôt
    (uses_locations), pas globalement.

D5  Variantes, lots, réservations et sessions d'inventaire sont
    créés comme entités à part entière (étapes 4-6) puisque le doc 14
    les considère acquis ; toutes les FK correspondantes sont
    nullables pour ne pas bloquer les magasins qui ne les utilisent
    pas.

D6  Hors ligne : les opérations à état partagé (workflow de
    transfert, validation d'inventaire) sont online-only ; les
    opérations locales et idempotentes (mouvements, transfert
    immédiat, comptage) restent offline (RÈGLE 9 doc 04).


============================================================
DECISIONS POUR LA PARTIE B
============================================================

D7  Toute entrée de stock a un coût : StockEntryForm devient une
    réception directe (étape 9.2). C'est la condition pour que la
    marge et la valorisation soient fiables ; sans cela, le
    reporting marge (13.2) est faux.

D8  Valorisation au coût moyen pondéré par défaut, FIFO en option.
    Le PMP est simple à expliquer et suffisant pour le commerce de
    détail ; FIFO est réservé aux activités à péremption (lots).

D9  Une seule séquence de numérotation par type de document et par
    entreprise (11.7), sans trou, verrouillée en base. Les numéros
    générés hors ligne sont provisoires (préfixe OFF-) et remplacés
    par un numéro définitif à la synchronisation ; le ticket
    réimprimé porte le numéro définitif.

D10 Mode simple par défaut (16.1). Toute nouvelle fonctionnalité de
    la Partie A ou B doit être invisible tant qu'elle n'est pas
    activée pour l'entreprise ou le magasin. Règle de revue de code :
    "un caissier d'un magasin à un seul entrepôt ne doit voir aucun
    nouvel écran ni champ".

D11 Les tests d'isolation multi-tenant (15.1) et la CI (15.2) sont
    posés AVANT l'étape 1, pas après : chaque nouvelle table apporte
    un nouveau risque de fuite entre entreprises.
