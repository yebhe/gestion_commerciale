# MODULE PWA (PROGRESSIVE WEB APP)

## OBJECTIF

Transformer l'application en une Progressive Web App (PWA) afin qu'elle soit :

* installable sur ordinateur ;
* installable sur Android ;
* installable sur iPhone (selon les capacités de Safari) ;
* rapide ;
* utilisable avec une connexion instable ;
* capable de fonctionner hors ligne pour les fonctionnalités prévues.

Le module PWA doit être développé comme un module indépendant afin de faciliter sa maintenance et son évolution.

---

# OBJECTIFS FONCTIONNELS

Le module PWA doit permettre :

✓ l'installation de l'application

✓ le fonctionnement plein écran

✓ la mise en cache des ressources

✓ la gestion du mode hors ligne

✓ la synchronisation automatique

✓ la détection de l'état du réseau

✓ les mises à jour de l'application

✓ une expérience utilisateur proche d'une application native.

---

# STRUCTURE RECOMMANDÉE

```text
pwa/
│
├── manifest
├── service_worker
├── offline_manager
├── cache_manager
├── sync_manager
├── network_manager
├── indexeddb
├── install_manager
├── update_manager
└── notification_manager
```

---

# MANIFEST

Le manifest doit contenir au minimum :

* nom complet
* nom court
* description
* icônes
* couleurs
* mode d'affichage
* orientation
* page de démarrage

---

# INSTALLATION

L'application doit pouvoir être installée sur :

* Android
* Windows
* macOS
* Linux

L'utilisateur doit recevoir une invitation d'installation uniquement lorsque cela est pertinent.

Ne jamais afficher cette invitation de manière intrusive.

---

# SERVICE WORKER

Le Service Worker doit gérer :

* cache des fichiers statiques
* cache des polices
* cache des images
* cache du shell de l'application
* stratégie de mise à jour
* suppression des anciens caches

Le Service Worker ne doit jamais contenir de logique métier.

---

# INDEXEDDB

IndexedDB est utilisée uniquement pour le stockage local.

Peuvent être stockés :

* produits
* catégories
* clients
* paramètres
* utilisateur connecté
* permissions
* sessions POS
* ventes en attente
* brouillons
* préférences utilisateur

Ne jamais stocker :

* mot de passe
* secret
* clé privée
* données bancaires
* token sensible

---

# MODE HORS LIGNE

Le mode hors ligne doit permettre :

* consulter les produits
* consulter les catégories
* consulter les clients
* utiliser le POS
* créer des ventes
* enregistrer des brouillons

Les opérations sont placées dans une file d'attente puis synchronisées lorsque la connexion revient.

---

# SYNCHRONISATION

Lors du retour de la connexion :

* détecter le réseau
* synchroniser automatiquement
* traiter les opérations dans l'ordre
* supprimer les opérations réussies
* conserver celles en erreur
* permettre une nouvelle tentative

Toutes les synchronisations doivent être journalisées.

---

# GESTION DES CONFLITS

En cas de conflit :

Exemple :

Deux utilisateurs modifient le même produit.

Le système doit :

* détecter le conflit
* empêcher l'écrasement silencieux
* informer l'utilisateur
* proposer une résolution

Aucune donnée ne doit être perdue sans avertissement.

---

# ÉTAT DU RÉSEAU

Le système doit détecter :

✓ connecté

✓ hors ligne

✓ connexion lente

✓ synchronisation en cours

✓ synchronisation terminée

L'utilisateur doit toujours connaître l'état actuel.

---

# CACHE

Mettre en cache :

* ressources statiques
* images fréquentes
* logos
* polices
* configuration

Ne pas mettre en cache inutilement les données dynamiques volumineuses.

---

# MISES À JOUR

Lorsqu'une nouvelle version est disponible :

Afficher un message personnalisé.

Exemple :

"Une nouvelle version est disponible."

Bouton :

Mettre à jour

Ne jamais recharger automatiquement l'application sans prévenir l'utilisateur.

---

# NOTIFICATIONS

Toutes les notifications doivent respecter le design de l'application.

Interdits :

* alert() JavaScript
* pop-up navigateur
* messages natifs du système

Utiliser uniquement :

* Toast
* Snackbar
* Modal personnalisée
* Bannière personnalisée

---

# SÉCURITÉ

HTTPS obligatoire.

Les données locales doivent respecter les mêmes règles de sécurité que le serveur.

Déconnexion :

Toutes les données sensibles doivent être nettoyées lors de la déconnexion.

# POINTS CRITIQUES À SURVEILLER

## 1. Ne jamais considérer IndexedDB comme la source de vérité

La base de données serveur reste toujours la référence.

---

## 2. Gérer correctement les conflits

Deux appareils peuvent modifier les mêmes données.

Une stratégie de résolution est indispensable.

---

## 3. Nettoyer le cache

Supprimer automatiquement les anciennes versions du cache après une mise à jour.

---

## 4. Limiter les données stockées

Ne synchroniser que les données réellement nécessaires au mode hors ligne.

---

## 5. Sécuriser les données locales

Ne jamais stocker :

* mots de passe
* secrets
* clés privées
* informations bancaires

---

## 6. Prévoir les UUID

Toutes les opérations hors ligne doivent utiliser des UUID afin d'éviter les collisions lors de la synchronisation.

---

## 7. Gérer les échecs de synchronisation

Une synchronisation échouée ne doit jamais entraîner une perte de données.

Les opérations doivent rester dans la file d'attente jusqu'à leur réussite.

---

## 8. Informer l'utilisateur

Toujours afficher clairement :

* hors ligne
* synchronisation en cours
* synchronisation réussie
* synchronisation échouée

---

## 9. Tester les scénarios réels

Tester systématiquement :

* coupure Internet pendant une vente ;
* fermeture du navigateur pendant une synchronisation ;
* reconnexion après plusieurs heures ;
* utilisation simultanée sur plusieurs appareils.

---

## 10. Isoler les données des entreprises

Même dans IndexedDB, toutes les données doivent être isolées par :

* company_uuid
* store_uuid (si nécessaire)

Aucune donnée d'une entreprise ne doit être accessible à une autre après un changement de compte ou de société.

---

# PRINCIPE FINAL

Le mode hors ligne est une amélioration de l'expérience utilisateur.

Il ne doit jamais compromettre :

* la sécurité ;
* l'intégrité des données ;
* l'isolation multi-tenant ;
* les permissions ;
* les règles métier.
